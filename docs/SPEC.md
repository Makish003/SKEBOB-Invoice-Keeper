## 1. Контекст

Команде нужно не забывать о регулярных платежах: аренда, подписки, серверы (с.2).
**Администратор** вносит регулярные платежи. **Пользователи** видят общий список, отмечают оплату и следят за просрочками.
Система напоминает об оплате **минимум за 3 дня до срока в Telegram-чат** и отвечает на вопросы «что и когда оплатить,
что уже оплачено, что просрочено» (с.2). Три валюты, без конвертации (с.3).

Жюри оценивает (с.17): **Польза**, **Корректность** (регулярность, напоминания, права доступа), **Удобство** (работоспособность и UX).
Стек, фоновые задачи и архитектура — на выбор команды. «Главное — понятное, обоснованное и работающее решение».

## 2. Глоссарий (с.5)

| Термин | Определение |
|---|---|
| Регулярный платёж (`RecurringPayment`) | Шаблон повторяющегося расхода: название, сумма, валюта, дата ближайшей оплаты, периодичность. |
| Период / платёж (`PaymentOccurrence`) | Конкретный экземпляр регулярного платежа с **собственной** датой срока (`due_date`) и **собственной** отметкой оплаты. |
| Оплачено | Оплата за период подтверждена, указана фактическая дата (`paid_at`). |
| Не оплачено | Оплата не подтверждена. При отмене отметки `paid_at` очищается. |
| Просрочка | Наступает **со следующего дня** после `due_date`. Оплата **в день срока — вовремя**. Вычисляется, не хранится. |
| Напоминание | Сообщение в Telegram-чат о неоплаченном периоде, не позднее чем за 3 дня до срока. |

## 3. Функциональные требования

### Данные и регулярность
- **FR-1** MUST: регулярный платёж хранит: название, сумму, валюту (RUB/USD/EUR), дату ближайшей оплаты, периодичность (с.4).
- **FR-2** MUST: поддержана периодичность «ежемесячно». MAY: другие периоды (еженедельно, ежеквартально, ежегодно) (с.4).
- **FR-3** MUST: единый часовой пояс приложения задаётся в `.env` (`APP_TIMEZONE`); «сегодня» вычисляется в нём (с.4).
- **FR-4** MUST: если в месяце нет числа исходной даты — срок = последний день месяца; в следующих месяцах число **возвращается** к исходному (31.01 → 28/29.02 → 31.03) (с.4).
- **FR-5** MUST: каждый период имеет свою дату срока и свою отметку «Оплачено / Не оплачено» (с.4, с.5).
- **FR-6** MUST: появление нового периода не стирает прошлые периоды и их оплаты; просрочка не останавливает генерацию следующих периодов (с.5, с.10).

### Статусы и просрочка
- **FR-7** MUST: отметить период оплаченным с фактической датой оплаты; отменить отметку (дата очищается) (с.5, с.11).
- **FR-8** MUST: исправить фактическую дату оплаты; просрочка пересчитывается, срок (`due_date`) не меняется (с.5).
- **FR-9** MUST: просрочка = (не оплачено И сегодня > срок) ИЛИ (оплачено И `paid_at` > срок). Оплата в день срока — вовремя (с.5).
- **FR-10** MUST: отметка оплаты относится только к конкретному периоду; история оплат сохраняется (с.7).

### Роли и права
- **FR-11** MUST: две роли — администратор и пользователь (с.3, с.6).
- **FR-12** MUST: администратор задаётся через `.env`; его учётная запись не изменяется и не удаляется через панель/API (с.6, с.9).
- **FR-13** MUST: администратор: добавляет и удаляет регулярные платежи; создаёт, меняет и удаляет **обычных** пользователей; может всё, что пользователь (с.9).
- **FR-14** MUST: пользователь: видит общий список платежей; меняет статус «Оплачено/Не оплачено»; указывает и исправляет фактическую дату оплаты (с.9).
- **FR-15** MUST: ограничения прав действуют и в веб-панели, и в API (с.6, с.9, с.10).
- **FR-16** MUST: без авторизации панель и данные недоступны (с.10).

### Напоминания (Telegram)
- **FR-17** MUST: бот сам периодически проверяет сроки и пишет в Telegram-чат, указанный в настройках (с.8).
- **FR-18** MUST: напоминание отправляется минимум за 3 дня до срока и содержит: название, сумму, валюту, дату оплаты (с.7, с.8).
- **FR-19** MUST: если платёж добавлен позже чем за 3 дня до срока — напоминание отправляется **сразу** (с.7).
- **FR-20** MUST: без дублей — повторная проверка не создаёт повторное напоминание по тому же периоду (с.7, с.8).
- **FR-21** MUST: оплаченный период не вызывает напоминание (с.8).
- **FR-22** MUST: удалённый (прекращённый) регулярный платёж больше не создаёт напоминаний; история сохраняется (с.8, с.13).

### Валюты и итоги
- **FR-23** MUST: RUB, USD, EUR; суммы и итоги считаются **отдельно** по каждой валюте; конвертации и курсов нет (с.3, с.7, с.11).

### Веб-панель
- **FR-24** MUST: веб-панель с авторизацией; список показывает: название, сумму, валюту, срок, статус, дату оплаты, просрочку (с.6).

### API (с.12–14) — префикс `/api/v1`
- **FR-25** MUST: реализованы эндпоинты:

| Метод | Путь | Назначение | Доступ |
|---|---|---|---|
| POST | `/api/v1/auth/login` | Вход по логину и паролю | все |
| GET | `/api/v1/auth/me` | Текущий пользователь | авторизованные |
| POST | `/api/v1/auth/logout` | Завершение текущей сессии | авторизованные |
| GET | `/api/v1/recurring-payments` | Список регулярных платежей | авторизованные |
| POST | `/api/v1/recurring-payments` | Создание регулярного платежа | admin |
| DELETE | `/api/v1/recurring-payments/{id}` | Прекращение платежа и его напоминаний **с сохранением истории** | admin |
| GET | `/api/v1/payment-occurrences` | Список периодов (в т.ч. оплаченные и просроченные) | авторизованные |
| GET | `/api/v1/payment-occurrences/{id}` | Конкретный период | авторизованные |
| PATCH | `/api/v1/payment-occurrences/{id}` | Подтверждение/отмена оплаты, исправление фактической даты | авторизованные |

| GET | `/api/v1/docs` | Swagger UI | все |

- **FR-26** MUST: к решению приложена OpenAPI-спецификация (`docs/openapi.yml`) и работающий Swagger на `/api/v1/docs` (с.14).
- **FR-27** MAY: дополнительные фичи — с произвольными эндпоинтами (с.13).

### Передача решения
- **FR-28** MUST: код, README с полной инструкцией запуска, `.env.example` без секретов, тестовые данные (аренда в RUB, сервер в USD, подписка в EUR) (с.4, с.10, с.11).

### Дополнительно (бонусы жюри, с.16) — MAY

- **FR-B2** Логи: авторизация и действия (журнал аудита).
- **FR-B3** Календарь оплат.
- **FR-B4** Итоги на дату по валютам.

## 4. Нефункциональные требования

- **NFR-1** Запуск одной командой по README (`docker compose up -d --build`) на чистой машине с Docker (Windows/macOS/Linux). Жюри запускает строго по README (с.10).
- **NFR-2** Персистентность: все данные сохраняются после перезапуска контейнеров (volume Postgres) (с.11).
- **NFR-3** Безопасность: пароли — argon2/bcrypt; сессии — серверные, отзываемые; секреты только в `.env`; `.env` в `.gitignore`; авторизация проверяется на сервере для каждого эндпоинта.
- **NFR-4** Корректность дат: все даты сроков/оплат — тип `DATE` без времени; «сегодня» = текущая дата в `APP_TIMEZONE`.
- **NFR-5** Деньги: `NUMERIC(14,2)` / `Decimal`, в JSON — строкой (`"85000.00"`), никаких float.
- **NFR-6** Идемпотентность напоминаний гарантируется на уровне БД (уникальный ключ), а не только кодом.
- **NFR-7** UI на русском, адаптивный (≥ 360px), доступный (WCAG 2.2 AA: контраст, фокус, клавиатура, `prefers-reduced-motion`).
- **NFR-8** Тесты: unit на доменную логику дат/просрочки/напоминаний, интеграционные на API и права, e2e на демо-сценарий.
- **NFR-9** Работоспособность без Telegram-токена: приложение стартует, напоминания пишутся в лог (режим `console`), README объясняет, как подключить бота.

## 5. Критерии приёмки (с.10–11, Given/When/Then)

| ID | Критерий | Ссылки |
|---|---|---|
| **AC-1** Запуск | Given чистая машина с Docker, When выполнить шаги README, Then панель открывается на `http://localhost:8080`, Swagger на `/api/v1/docs`, есть тестовые данные. | NFR-1, FR-28 |
| **AC-2** Доступ | Given нет сессии, When запрос к любому `/api/v1/*` кроме `auth/login` и `docs`, Then `401`; панель редиректит на `/login`. | FR-16 |
| **AC-3** Роли | Given вход пользователем, When `POST/DELETE /recurring-payments`, любые `/users` — Then `403`, данные не изменены. Кнопок админ-действий в UI нет. | FR-13..15 |
| **AC-4** Админ из .env | Given admin из `.env`, When `PATCH/DELETE /users/{admin_id}` — Then `403`; создать пользователя с ролью admin нельзя. | FR-12 |
| **AC-5** Регулярность | Given ежемесячный платёж 31.01, When наступает следующий период, Then существует отдельный период 28/29.02 со статусом «Не оплачено», январский период и его оплата сохранены; затем 31.03. | FR-4..6 |
| **AC-6** Напоминание | Given неоплаченный период со сроком через ≤ 3 дня, When срабатывает проверка, Then в чат уходит **одно** сообщение с названием, суммой, валютой, датой; повторные проверки дублей не создают. | FR-17,18,20 |
| **AC-7** Сразу | Given создаётся платёж со сроком через 1 день, When POST выполнен, Then напоминание уходит без ожидания планового тика (≤ 1 мин). | FR-19 |
| **AC-8** Оплачено → без напоминания | Given период оплачен до входа в окно 3 дней, When проверка, Then напоминание не отправляется. | FR-21 |
| **AC-9** Отметка/отмена | Given неоплаченный период, When PATCH `status=paid, paid_at`, Then статус «Оплачено»; When PATCH `status=unpaid`, Then `paid_at = null`. | FR-7 |
| **AC-10** Исправление даты | Given период оплачен с `paid_at > due_date` (просрочка), When PATCH `paid_at = due_date`, Then `is_overdue = false`, `due_date` не изменился. | FR-8, FR-9 |
| **AC-11** Просрочка | Given неоплаченный период, When сегодня = `due_date` → не просрочен; When сегодня = `due_date + 1` → просрочен на 1 день. | FR-9 |
| **AC-12** Валюты | Given платежи в RUB, USD, EUR, When `GET /payments/summary`, Then три отдельные суммы, без конвертации. | FR-23 |
| **AC-13** Сохранение | Given данные созданы, When `docker compose restart` / `down` + `up`, Then все данные на месте. | NFR-2 |
| **AC-14** Удаление | Given регулярный платёж удалён, When проверка напоминаний и генерация периодов, Then новых напоминаний и периодов нет; прошлые периоды и оплаты видны в истории. | FR-22 |
| **AC-15** Передача | В репозитории: код, README, `.env.example` без секретов, тестовые данные, `docs/openapi.yml`. | FR-26, FR-28 |

## 6. Граничные случаи

- **EC-1** Срок 29/30/31 числа → короткие месяцы, високосный год (29.02.2028).
- **EC-2** Платёж создан с датой в прошлом → генерируются все периоды с этой даты (будут просрочены) — это валидный сценарий для демо просрочки.
- **EC-3** Платёж создан со сроком сегодня или завтра → напоминание сразу (FR-19).
- **EC-4** `paid_at` в будущем → `422`. `paid_at` раньше срока → допустимо (ранняя оплата).
- **EC-5** PATCH `paid_at` у неоплаченного периода без `status=paid` → `422`.
- **EC-6** Telegram недоступен / неверный токен → напоминание остаётся в статусе `failed`, ретрай с backoff, не более N попыток; без дублей после успеха.
- **EC-7** Воркер упал между отправкой и фиксацией → допускается максимум один дубль (at-least-once), фиксируется в DECISIONS; окно минимизировано «claim → send → mark sent».
- **EC-8** Удалённый пользователь → его сессии аннулированы, логин невозможен; его прошлые отметки оплат сохраняются (`paid_by` = snapshot имени).
- **EC-9** Смена `APP_TIMEZONE` → даты сроков не сдвигаются (тип DATE), меняется только «сегодня».
- **EC-10** Повторный POST одного и того же платежа — разрешён (это разные платежи); дубликаты периодов внутри платежа запрещены `UNIQUE(recurring_payment_id, due_date)`.
- **EC-11** Удаление уже удалённого платежа → `404` или идемпотентный `204` (выбрать и задокументировать).
- **EC-12** Пользователь пытается сменить свою роль/логин admin через PATCH → `403`.

## 7. Вне рамок (Out of Scope)

- **OS-1** Конвертация валют и курсы (прямо исключено ТЗ, с.3).
- **OS-2** Управление учётками администраторов через панель (с.6).
- **OS-3** Реальная оплата / платёжные шлюзы.
- **OS-4** Мультитенантность, несколько Telegram-чатов на разные команды (один чат из `.env`; MAY — переопределение в настройках).
- **OS-5** Мобильные приложения (адаптивная веб-панель достаточна).
