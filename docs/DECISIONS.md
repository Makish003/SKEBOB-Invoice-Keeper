# DECISIONS — архитектурные решения (ADR-lite)

Формат: `ADR-NNN · статус (accepted/superseded) · контекст → решение → последствия`.
Новые решения агент добавляет в конец и ссылается на них в журнале `PLAN.md §9`.

---

**ADR-001 · accepted · Монорепо, docker compose как единственный способ запуска.**
Жюри запускает строго по README (AC-1) на неизвестной ОС → один `docker compose up -d --build`, никаких локальных Python/Node у жюри.

**ADR-002 · accepted · Backend: Python 3.12 + FastAPI + SQLAlchemy 2 (sync) + Alembic + PostgreSQL 16.**
FastAPI даёт Swagger на произвольном пути (`docs_url="/api/v1/docs"`) и экспорт OpenAPI (FR-26). Sync-ORM проще и надёжнее под хакатон;
нагрузка мизерная. Postgres нужен ради `ON CONFLICT` и `FOR UPDATE SKIP LOCKED` (NFR-6).

**ADR-003 · accepted · Фоновые задачи — отдельный сервис `worker` (APScheduler + aiogram 3, long polling).**
Планировщик внутри uvicorn задублируется при нескольких воркерах и мешает тестам. Polling (а не webhook) — потому что у жюри нет публичного HTTPS.

**ADR-004 · accepted · Периоды (occurrences) материализуются в БД заранее на горизонт 35 дней (минимум один будущий).**
Альтернатива «вычислять на лету» ломает хранение отметок оплаты по периодам и историю (FR-5, FR-6). Горизонт гарантирует, что «следующий период» виден на демо.

**ADR-005 · accepted · Ежемесячный срок считается от `anchor_day` исходной даты, а не от предыдущего срока.**
Иначе 31.01 → 28.02 → 28.03 («дрейф»). Правильно: 31.01 → 28/29.02 → 31.03 (FR-4).

**ADR-006 · accepted · Просрочка вычисляется, не хранится.**
Зависит от «сегодня» и `paid_at`; хранение потребовало бы пересчётов и порождало бы рассинхрон (FR-8, FR-9).

**ADR-007 · accepted · Дедупликация напоминаний — `UNIQUE(occurrence_id, channel, kind)` в таблице `reminders`; доставка at-least-once.**
Claim (`INSERT … ON CONFLICT DO NOTHING`) → send → mark sent. Теоретический дубль возможен только при падении процесса между send и commit — окно миллисекунды, задокументировано (EC-7).

**ADR-008 · accepted · Удаление регулярного платежа — soft delete (`deleted_at`).**
ТЗ (с.13): «прекращение … с сохранением истории». Прошлые периоды и оплаты остаются видимыми, новые периоды и напоминания не создаются, `pending`-напоминания отменяются.

**ADR-009 · accepted · Сессии серверные (таблица `sessions`), токен в httpOnly-cookie + Bearer для Swagger.**
JWT без серверного состояния не даёт честного `logout` («завершение текущей сессии», с.12) и немедленного отзыва при удалении пользователя.

**ADR-010 · accepted · Деньги — `NUMERIC(14,2)`/`Decimal`, в JSON строкой; без конвертации.**
Float даёт ошибки округления в итогах; конвертация прямо исключена (OS-1).

**ADR-011 · accepted · Часы приложения инъецируются (`Clock`), `CLOCK_OVERRIDE` разрешён только при `APP_ENV != production`.**
Нужно для детерминированных тестов дат и для демонстрации «следующего периода» вживую.

**ADR-012 · accepted · Frontend: React 19 + Vite + TS + Tailwind v4 + shadcn/ui + TanStack Query + motion; типы из `docs/openapi.yml`.**
SPA за nginx с proxy `/api` — один origin, cookie без CORS. Контракт-first позволяет двум агентам работать параллельно.

**ADR-013 · accepted · Дизайн-доктрина — ux-ui-agent-skills (XIAS) + Motion AI Kit.**
Токены по смыслу, 8 состояний компонентов, объективные гейты (контраст, клавиатура, reduced motion). Анимации только transform/opacity.
Конкретное визуальное направление выбирает FRONT в F-02 и дописывает сюда (ADR-014).

**ADR-014 · accepted · Уникальность логина — частичный индекс `UNIQUE(login) WHERE deleted_at IS NULL`.**
Пользователи удаляются мягко (EC-8: их прошлые отметки оплат сохраняются). Полный UNIQUE запретил бы повторно выдать логин
удалённого сотрудника. Активные логины по-прежнему уникальны (дубль → `409`).

**ADR-015 · accepted · Frontend-инструменты: компоненты в стиле shadcn пишутся вручную на `radix-ui`; TypeScript 5.9; линтер oxlint.**
`shadcn init` в неинтерактивном режиме зависает на выборе пресета — компоненты (Button, Select, Dialog, Popover…) пишутся
в `src/components/ui` по тем же паттернам на Radix-примитивах и наших токенах. TypeScript закреплён на 5.9: `openapi-typescript@7`
требует TS 5 (peer). Линтер — oxlint из шаблона Vite (совместимые с ESLint правила, на порядок быстрее); «eslint чистый» в
quality bar читается как «oxlint без ошибок».

**ADR-016 · superseded by ADR-024 (палитра, шрифты, логотип) · Визуальное направление: linear-app (XIAS), светлая тема по умолчанию + нативная тёмная.**
Бриф: финтех-операции для небольшой команды, тон спокойный и утилитарный, настроение «точный», моушн — subtle feedback.
Палитра почти ахроматическая, единственный акцент — индиго `#5e6ad2`; статусы периодов — иконка + текст + тон
(success/warning/info/danger/neutral). Inter Variable (кириллица) с `cv01, ss03, tnum`, базовый кегль 14px (плотные таблицы),
заголовок страницы ≥ 2.5× base. Токены: `frontend/src/styles/tokens.css` (примитивы → семантика, тёмная тема меняет только
семантику) → `@theme inline` Tailwind. Все пары текст/фон и контролы проверены `contrast.py` (≥ 4.5:1 текст, ≥ 3:1 границы
контролов). Тема: светлая/тёмная/системная, выбор хранится в localStorage.

**ADR-017 · accepted · Прекращение платежа удаляет только будущие неоплаченные периоды; повторное удаление → 404 (EC-11).**
История — это прошлые периоды и все оплаты: они остаются и видны с `include_deleted=true`. Неоплаченные периоды со сроком
позже сегодняшнего дня ещё не наступили, поэтому удаляются вместе с их напоминаниями; открытые напоминания остальных
периодов переводятся в `cancelled`. Список периодов и итоги по умолчанию показывают только активные платежи, чтобы
прекращённый платёж не «висел» в работе; история доступна фильтром. Повторный DELETE — `404` (объекта для прекращения нет).

**ADR-018 · accepted · Поля API — snake_case; замечания `api-design-reviewer` про camelCase/HATEOAS/кэш не применяются.**
Контракт §1.5 и ТЗ (`first_due_date`, `paid_at`, `recurring_payment_id`) — snake_case; менять его нельзя (CLAUDE.md, «Не ломать
контракт»). Линтер: 90.7/100, 0 ошибок; оставшиеся предупреждения — camelCase (54) и `422` у path-параметров (FastAPI валидирует
`int`). Скоркард F (59/100) построен на эвристиках (ссылки между ресурсами, Cache-Control, пакетные операции), которые для
внутренней панели с авторизацией по сессии не дают пользы; пагинация и фильтры у списка периодов есть (`limit/offset/total`).

**ADR-019 · accepted · Напоминания о просрочке: ключ дедупликации расширен днём — `UNIQUE(occurrence_id, channel, kind, remind_on)`.**
Бонус FR-B10: о неоплаченном просроченном периоде бот напоминает не чаще раза в день и не больше `OVERDUE_REMINDER_MAX` раз
(по умолчанию 3, `0` — выключено). Чтобы гарантия «без дублей» осталась на уровне БД (ADR-007), в ключ добавлен `remind_on`:
для `upcoming` это срок периода (по-прежнему ровно одно напоминание), для `overdue` — день напоминания. Лимит считается подзапросом
при постановке. Перед отправкой overdue-напоминание отменяется, если период оплачен или платёж прекращён. Напоминаем только о просрочках
не старше `OVERDUE_REMINDER_WINDOW_DAYS` (30): иначе платёж, созданный задним числом, засыпал бы чат (тест: 105 → ≤ 5).

**ADR-020 · accepted · Фаза 5 «продуктовое усиление» после M4 — отдельной веткой, контракт только расширяется.**
Решение сдано (тег `v1.0.0`), но для ежедневного использования мешали: засорение демо-базы e2e-тестами, запись в БД и N+1 на
каждом GET, невозможность исправить платёж, перегруженная сводка. Работа идёт в ветке `improve/product-hardening`; пути и поля
FR-25 не меняются, добавляются только новые эндпоинты/поля. E2E — на отдельном compose-проекте (`compose.e2e.yml`, порт 8081,
внешние каналы выключены: два воркера с одним токеном бота конфликтуют на `getUpdates`).

**ADR-021 · accepted · Материализация периодов: воркер — основной источник, чтение — дешёвая догоняющая проверка.**
Варианты: (а) убрать материализацию из GET полностью — тогда при остановленном воркере или после смены даты (`CLOCK_OVERRIDE`,
полночь) списки и итоги временно не видят новый период, а AC-5 зависит от интервала тика; (б) оставить как было — 1 + N запросов
и COMMIT на каждом GET. Выбрано (в): `ensure_all` делает один `SELECT … GROUP BY` по активным платежам, недостающие периоды
считаются в памяти и вставляются одним `INSERT … ON CONFLICT DO NOTHING`; GET коммитит, только если что-то создано. В
установившемся режиме чтение не пишет в БД, число запросов не зависит от числа платежей (тест `test_query_budget`).

**ADR-022 · accepted · Изменение платежа: название, описание и сумма; валюта и график — только через новый платёж.**
В реальной работе цена меняется (индексация аренды, новый тариф), а прекращать и пересоздавать платёж ради этого — терять
связь истории. `PATCH /recurring-payments/{id}` (админ, `FOR UPDATE`, аудит `recurring_payment.updated` с «было/стало»).
Новая сумма применяется к шаблону и к неоплаченным периодам со сроком **сегодня или позже**: оплаченные — как платили,
уже просроченные — долг в прежней сумме (выставленный счёт не переписывается задним числом). Смена валюты исказила бы итоги
по валютам за прошлые месяцы, смена графика — номера и сроки периодов с отметками оплат; для этого прекращают платёж и создают
новый. Прекращённый платёж не меняется (`409`).

**ADR-023 · accepted · Telegram-бот — упрощённая панель; доступ по членству в командном чате.**
Кроме напоминаний бот показывает сводку, ближайшие сроки, просрочки, итоги месяца, платежи и карточку периода с отметкой и
снятием оплаты. Экраны — чистые функции над БД (`services/telegram_screens.py`), навигация редактирует одно сообщение
(`CallbackData` aiogram ≤ 64 байт), цвет кнопок — поле `style` Bot API. Доступ: (а) только чат `TELEGRAM_CHAT_ID` — неудобно
смотреть сроки в личке; (б) любой, кто знает бота — утечка сумм. Выбрано (в): командный чат по id и личные чаты тех, кто
состоит в нём (`getChatMember`, кеш 5 минут); проверка — на каждое нажатие, поэтому кнопки меню без HMAC (подпись оставлена у
«Оплачено» в напоминании). Ссылки на сайт — `PUBLIC_URL`, по умолчанию `https://DOMAIN` или `http://localhost:WEB_PORT`;
Telegram отклоняет кнопки с localhost, поэтому локально адрес копируется кнопкой `copy_text`, а Mini App включается только по HTTPS.

**ADR-024 · accepted · Фирменный стиль Aéza (гайдбук 2026) вместо направления linear-app; структура токенов ADR-016 сохранена.**
Решение размещено на инфраструктуре Aéza, интерфейс переведён в её айдентику (гайдбук: `docs/aeza-guidebook-2026.pdf`). Цвета гайдбука: чёрный `#000`, акцент `#4CC6F1`
(PANTONE 298 C), фон `#F4F4F4`; дополнительные `#182D48` (тёмно-синий: выбор и info в тёмной теме) и `#E97C35` (оттенки для
warning). Белый текст на `#4CC6F1` даёт 1.97:1, поэтому основная кнопка — чёрный текст на голубом (10.7:1), а для текста, ссылок
и фокуса в светлой теме — затемнённый `#0B6F94` (5.1–5.7:1); у destructive отдельный токен `text-on-destructive` (белый).
Шрифты: Exo 2 (заголовки страниц, крупные числа, названия карточек; заголовки страниц — прописные, как в гайдбуке) и Inter
(всё остальное, без изменений). Логотип — строчные буквы на «клавишах» по конструкции знака Aéza («i», «k» + название Exo 2);
сам знак Aéza не используется, чтобы не выдавать продукт за продукт компании. Иконки разделов — на фирменной плитке (чёрная
клавиша, голубой знак) у активного пункта; переключатели — «нажатая клавиша». Фирменный паттерн (параллельные линии и линия со
скруглённым поворотом) — только на экране входа, в чёрной брендовой панели. Скругления увеличены до пропорций клавиш (6–16px).
Альтернативы: (а) тёмная тема по умолчанию, как в панели Aéza — отвергнута, светлая остаётся по умолчанию, тёмная доступна;
(б) голубые заливки крупных блоков — отвергнута, один акцент и нейтрали несут вес.

**ADR-025 · accepted · Логотип «Клавиша IK» вместо двух клавиш «i k»; дополняет ADR-024.**
Знак: одна клавиша Aéza (скругление 25 % стороны), на ней I и K, у которой плечи образуют голубую галочку «оплачено». Свой знак,
а не изменённый логотип Aéza; из гайдбука взяты только конструкция клавиши, цвета и Exo 2. Название рядом со знаком набрано
строчными Exo 2 Bold, как в утверждённой подписи из `brand/` (прописные Exo 2 по ADR-024 остаются у заголовков страниц).
В интерфейсе знак рисуется inline-SVG через токены `brand-key`, `brand-key-fg`, `brand-accent`, поэтому в тёмной теме клавиша
светлеет; при 28px используется мелкая версия знака (толще штрихи). Favicon (`.ico` 16/32/48 и SVG с `prefers-color-scheme`),
иконки 180/192/512 (+ maskable) и `site.webmanifest` лежат в `frontend/public/`. Полный комплект (варианты, подписи,
аватарка бота, презентация, правила использования) в `brand/`. Альтернативы: (а) строки фирменного паттерна как знак похожи
на иконку меню; (б) чек с бейджем: привычная для темы картинка, хуже запоминается.

**ADR-026 · accepted · Фирменный паттерн строго по стр. 22 гайдбука; линии всегда уходят за край кадра; дополняет ADR-024.**
На экране входа паттерн был SVG-полосой фиксированной высоты со `slice`-масштабированием: верх полосы срезался, и линии
начинались в воздухе посреди панели. Гайдбук (`docs/aeza-guidebook-2026.pdf`, стр. 22): три прямые параллельные линии и одна
акцентная линия контрастного цвета, которая идёт параллельно и поворачивает с плавным скруглением; на образце линии выходят за
края кадра. `BrandPattern` собран из CSS-рамок, привязанных к краям контейнера, поэтому концы за краем при любом размере.
Композиция `panel` (панель входа) повторяет стр. 22: три белые вертикали на всю высоту у левого края поверх трёх голубых
горизонталей у нижнего, голубая акцентная линия спускается сверху правее вертикалей и поворачивает к правому краю. Толщина
около половины шага, как на образце. Текст панели стоит правее акцентной вертикали и выше её поворота, поэтому линии его не
пересекают; заголовок на 1024–1279px уменьшен до 4xl, чтобы поместиться. Вариант `strip` (основание боковой панели и мобильного
меню, под профилем): верхний край там не край кадра, вертикали на всю высоту прошли бы через навигацию, поэтому три голубые
горизонтали и одна акцентная линия цвета `brand-pattern-line` (чёрный в светлой теме, #F4F4F4 в тёмной), которая поднимается от
низа и уходит вправо. Ограничение ADR-024 «паттерн только на входе» снято только для этих двух мест. Отвергнуто: (а) угол карточки
сводки с тремя поворачивающими линиями: такой композиции нет в гайдбуке, а три прямые на всю высоту карточки легли бы на цифры;
(б) паттерн за заголовком страницы спорит с действиями шапки; (в) в пустых состояниях они мелкие, паттерн превращается в шум.

**ADR-027 · accepted · `TELEGRAM_CHAT_ID` — список чатов; доставка в Telegram успешна, если дошло хотя бы в один чат.**
Команде нужны напоминания и меню не только в группе, но и в личке с ботом. `TELEGRAM_CHAT_ID` принимает несколько id через
запятую (точку с запятой или пробел), дубли отбрасываются. Напоминание уходит в каждый чат; кнопка «Оплачено» принимается из
любого. Доступ к меню: чат из списка — по id; личка — если человек состоит хотя бы в одной группе из списка (отрицательные id,
`get_chat_member` с кешем 5 минут); положительные id — личные чаты, членство в них не запрашивается. Канал по-прежнему один
(`telegram`), поэтому `UNIQUE` в `reminders` (ADR-007) не меняется: если часть чатов не приняла сообщение, а часть приняла,
отправка считается успешной, сбой пишется предупреждением в лог воркера; ретрай — только если не дошло никуда. Отвергнуто:
(а) строка `reminders` на каждый чат — миграция ключа ради редкого частичного сбоя; (б) ретрай при любом сбое — дубли в чатах,
где напоминание уже есть. `external_id` — message_id через запятую, обрезан до 64 символов колонки.

**ADR-028 · accepted · Паттерн на плитках: шапка раздела и плитка месяца в боковой панели; дополняет ADR-026, заменяет вариант `strip`.**
Полоса паттерна внизу боковой панели была единственным таким элементом и читалась как случайный разделитель: на стр. 22
гайдбука паттерн всегда лежит на скруглённой плитке и уходит за её края, а у полосы плитки не было. Теперь паттерн живёт на
плитках двух размеров той же формы, что панель входа: (1) шапка каждого раздела (`PageHeader`) — композиция стр. 22 справа
(три вертикали, голубой поворот и второй поворот цвета линий, горизонтали на всю ширину), слева заголовок, описание, действия
и ключевые цифры раздела (в журнале — события, входы и изменения за сегодня); (2) плитка текущего месяца в боковой панели
(`MonthPlate`) — миниатюра той же композиции и счёт периодов месяца «оплачено из», просрочено или осталось; ведёт на сводку.
Только количества: суммы разных валют не складываются. Цвет плитки по теме (`--brand-plate`, `--brand-plate-sidebar`): в тёмной
чёрная, как на стр. 22; в светлой светлая (белая на фоне страницы, светло-серая на белой панели) с чёрными вертикалями и голубыми
горизонталями — чёрные плитки на светлом интерфейсе выглядели чужеродно (прототип, отзыв пользователя). Действия шапки стоят под
текстом, над горизонталями, поэтому с паттерном не спорят — возражение (б) ADR-026 снято. На узком экране вертикали прижаты к
правому краю, второго поворота нет; на экране ниже 44rem плитка месяца скрыта, чтобы не теснить меню. Отвергнуто: (а) голубая
тонированная плитка в светлой теме — горизонтали на голубом фоне теряются; (б) чёрные плитки в обеих темах — выпадают из светлой.

**ADR-029 · accepted · Заявки администратору: тема из списка, описание, файлы и периоды платежей; права на сервере.**
Пользователю нужен канал «у меня вопрос или что-то сломалось», который не теряется в чатах. Заявка (`support_tickets`) — тема
из фиксированного списка (`question`, `bug`, `payment`, `access`, `other`), описание до 4000 символов, до 5 файлов и до 10
периодов платежей (`support_ticket_payments`, связь многие-ко-многим с `payment_occurrences`). Создаётся одним запросом
`multipart/form-data` (`POST /support-tickets`), поэтому заявка с файлами атомарна: файлы пишутся в том `uploads` до COMMIT и
удаляются при откате, проверка типа по сигнатуре та же, что у чеков (ADR к FR-B8, `ReceiptStorage`). Видимость: пользователь
видит только свои заявки, чужая для него — 404 (не 403, чтобы не раскрывать, что заявка есть); администратор видит все и один
меняет статус (`open` → `in_progress` → `resolved`) и ответ (`PATCH`, `require_admin`). Создание и обработка — в журнале аудита
(`ticket.*`, «было → стало»). Периоды прикладываются ссылкой, а не снимком: администратор видит текущую сумму и статус.
Отвергнуто: (а) создание JSON и отдельная загрузка файлов — заявка без файлов при сбое на втором шаге; (б) переписка
(несколько сообщений в заявке) — для хакатона хватает одного ответа администратора, модель расширяема таблицей сообщений;
(в) уведомление о новой заявке в Telegram — чаты бота общие для команды, заявка может быть личной.
